### BATCH 2 — Hardening: mime allow-list, EXIF stripping, date validation, migration safety

**Goal:** Fold the four "should fix" hardening items into one batch. All are small, tightly scoped, no UX changes.

**Files:**

- Modify: `server/routes/biometrics.ts` (mime filter, date validation)
- Modify: `server/services/fileUpload.ts` (EXIF stripping in `uploadImage()`) — verify the function exists and adds `.withMetadata({ exif: {} })` or equivalent
- Modify: `server/migrations/011_biometrics_foundation.ts` (down() safety assertion)

**Steps:**

1. **Step 1: Mime allow-list**
   - File: `server/routes/biometrics.ts`, around line 44 (`fileFilter` in `photoUpload` multer config)
   - Replace:
     ```ts
     fileFilter: (_req, file, cb) => {
       if (file.mimetype.startsWith('image/')) cb(null, true);
       else cb(new Error('Only images allowed'));
     },
     ```
   - With:

     ```ts
     const ALLOWED_PHOTO_MIME = new Set([
       'image/jpeg',
       'image/png',
       'image/webp',
       'image/heic',
       'image/heif',
     ]);

     // ... inside photoUpload config:
     fileFilter: (_req, file, cb) => {
       if (ALLOWED_PHOTO_MIME.has(file.mimetype)) cb(null, true);
       else cb(new Error('Unsupported image format. Use JPEG, PNG, WebP, or HEIC.'));
     },
     ```

   - Update the `handleUploadError` branch checking `'Only images allowed'` to also handle the new error message (or use a sentinel error).

2. **Step 2: EXIF stripping in sharp pipeline**
   - File: `server/services/fileUpload.ts`
   - Find `uploadImage()` and locate the `sharp(buffer).resize(...).webp(...)` chain.
   - Replace any `.withMetadata({...})` call (if present) with explicitly empty metadata:
     ```ts
     .withMetadata({}) // strip all EXIF including GPS
     ```
   - If no `.withMetadata` is currently called, ADD it before `.webp(...)`. Sharp strips by default but explicit is better. Add a comment: `// Explicit EXIF/GPS strip — photos may contain location data from camera apps.`
   - Also patch the dev base64 fallback in `server/routes/biometrics.ts` POST `/photos` handler: the inline `sharp(req.file.buffer).resize(...).webp(...)` calls also need `.withMetadata({})`.

3. **Step 3: Date validation on `recordedAt`**
   - File: `server/routes/biometrics.ts`, line 21-23 (`createBodyMetricsBodySchema`)
   - **Date floor decision: `2010-01-01`** (revised from initial `2020-01-01` proposal per review). Reasoning: GymGurus users importing historical data may be coming from MyFitnessPal (launched 2005), Withings (2009), Strong (2013), Apple Health (2014), or paper logbooks. A 50-year-old user might have records going back 10+ years. The floor is meant to prevent obvious typos (a stray `19` instead of `20` in the year), not gate legitimate history. `2010` covers the "modern fitness tracking" window without rejecting reasonable backfill. Anything older is rare enough that a 400 with a clear message is acceptable friction.
   - **Clock skew tolerance: 1-minute buffer on max** (per review). A user logging at 23:59:59 with a phone clock 30s fast shouldn't get rejected. Bake it in.
   - Replace:
     ```ts
     const createBodyMetricsBodySchema = insertBodyMetricsSchema.omit({ userId: true }).extend({
       recordedAt: z.coerce.date().optional(),
     });
     ```
   - With:

     ```ts
     // Date floor 2010 covers modern fitness tracking history (MyFitnessPal 2005,
     // Withings 2009, Apple Health 2014). Floor is for typo prevention, not
     // history gating. Ceiling is now+1min to absorb client clock skew without
     // false-rejecting near-midnight logs.
     const recordedAtSchema = z.coerce
       .date()
       .min(new Date('2010-01-01'), 'Date too far in the past')
       .max(new Date(Date.now() + 60_000), 'Cannot log future entries');

     const createBodyMetricsBodySchema = insertBodyMetricsSchema.omit({ userId: true }).extend({
       recordedAt: recordedAtSchema.optional(),
     });
     ```

   - Apply same to `updateBodyMetricsBodySchema` (it inherits via `.partial()` so this is automatic).

4. **Step 4: Down-migration safety assertion**
   - File: `server/migrations/011_biometrics_foundation.ts`, top of `down()` function
   - Add as the FIRST statement in `down()`:
     ```ts
     // Safety: refuse to down-migrate if any rows depend on user_id, because
     // dropping the column would silently destroy data. Force operator to
     // reconcile (delete the rows, OR migrate them to a different owner) first.
     const [{ count }] = await db.execute<{ count: number }>(sql`
       SELECT COUNT(*)::int AS count FROM progress_entries WHERE user_id IS NOT NULL
     `);
     if (count > 0) {
       throw new Error(
         `[Migration 011 down] BLOCKED: ${count} progress_entries rows have user_id NOT NULL. ` +
           `Dropping the column would destroy these rows silently. ` +
           `Reconcile the data manually before re-running down().`
       );
     }
     ```
   - Update the `console.warn` at the bottom of `down()` to mention "no user_id rows existed; safe to revert".

5. **Step 5: Verify TS + build**
   - `npx tsc --noEmit 2>&1 | grep -E "error TS" | wc -l` → 200
   - `npm run build` → clean

6. **Step 6: Smoke test**
   - Upload a JPG photo → succeeds
   - Try uploading an SVG → 400 with "Unsupported image format"
   - Log a body metric with `recordedAt` set to tomorrow → 400 "Cannot log future entries"
   - Log a body metric with `recordedAt` set to 1990-01-01 → 400 "Date too far in the past"
   - In dev, run `npx tsx server/migrations/011_biometrics_foundation.ts down` after manually inserting a progress_entries row with user_id NOT NULL → expect throw

### BATCH 3 — Consent toggle audit logging

**Goal:** Add structured audit log so consent flips can be reconstructed if ever disputed.

**Files:**

- Modify: `server/routes/settings.ts` (PATCH `/biometrics-sharing` handler)
- New (optional): `server/services/auditLog.ts` — only if a reusable audit-log helper doesn't already exist; otherwise inline a console-based structured log

**Steps:**

1. **Step 1: Check existing audit log infrastructure**
   - `grep -rn "auditLog\|logger\.audit\|audit_log" server/`
   - If a logger exists, use it. If not, use structured `console.log` with a clear prefix like `[AUDIT]`.

2. **Step 2: Log on consent change**
   - File: `server/routes/settings.ts`, inside `router.patch('/biometrics-sharing', ...)` handler
   - **Capture `previousValue` BEFORE the UPDATE** (per review). A consent log without the previous value tells you the destination state but not the transition. `{flag, value: false}` could mean "user just opted out" or "user reaffirmed an existing opt-out." Only `{flag, previousValue: true, value: false}` is a complete audit event.
   - Refactor the handler to:
     1. SELECT the current `shareBodyMetricsWithTrainer` for the user's matching client row
     2. UPDATE it
     3. Emit the audit log with both `previousValue` and `value`
   - Code shape:

     ```ts
     // Capture previous value so the audit log records the transition, not just
     // the destination. {flag, previousValue, value} is a complete audit event;
     // {flag, value} alone can't distinguish a flip from a reaffirm.
     const [existing] = await db
       .select({ shareBodyMetricsWithTrainer: clients.shareBodyMetricsWithTrainer })
       .from(clients)
       .where(and(eq(clients.email, user.email), isNull(clients.deletedAt)));
     const previousValue = existing?.shareBodyMetricsWithTrainer ?? null;

     await db
       .update(clients)
       .set({ shareBodyMetricsWithTrainer })
       .where(and(eq(clients.email, user.email), isNull(clients.deletedAt)));

     // Audit log — privacy-sensitive flag changes must be reconstructable.
     // Format: structured JSON line for log aggregator parsing.
     console.log(
       JSON.stringify({
         event: 'consent.toggled',
         userId: user.id,
         email: user.email,
         flag: 'shareBodyMetricsWithTrainer',
         previousValue,
         value: shareBodyMetricsWithTrainer,
         ts: new Date().toISOString(),
         ip: req.ip,
         userAgent: req.headers['user-agent'],
       })
     );
     ```

   - Note: `previousValue` is `null` only when the Disciple has no linked client row yet — a degenerate case (the toggle is invisible in the UI for that user, but the API can still be called). Logging `null` is honest and lets log analysis distinguish "first toggle ever" from "flip" from "reaffirm."

3. **Step 3: Verify TS + build**
   - Same gates as before.

4. **Step 4: Smoke test**
   - Login as Disciple, toggle the Privacy switch ON → check server logs for `[AUDIT] consent.toggled`-like line
   - Toggle OFF → another log line
   - Verify the log line is parseable as JSON (paste into `JSON.parse()` mentally, or grep + jq)

5. **Step 5: Commit**
   ```bash
   git commit -m "feat(audit): SPRINT 1.5 BATCH 3 — structured audit log on consent toggle"
   ```
